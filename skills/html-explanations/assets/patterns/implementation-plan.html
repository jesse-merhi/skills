Implementation plan · ready to build

Make every retry state visible.

Add one shared retry-state contract, expose it through the existing job API, then render the same language in list and detail views. No queue-policy change is part of this plan.

Target behaviorA person can see attempt count, next retry time, and terminal failure without reading logs.

Dependency order

  1. Contract

    Define and validate the shared retry state at the API boundary.

  2. Read model

    Return state, attempts, and next-attempt time from the existing endpoint.

  3. Interface

    Render the contract in list and detail views with one vocabulary.

Work slices

Backend seam

  • Add RetryState in the shared domain module.
  • Validate persisted state before serializing the response.
  • Prove scheduled, retrying, and exhausted mappings.

User-facing seam

  • Reuse the existing status component.
  • Show absolute time with a relative-time supplement.
  • Keep terminal recovery action keyboard reachable.

Risks and controls

Contract drift

List and detail views derive labels separately.

One shared formatter with fixture coverage.
Time ambiguity

Relative time becomes stale or hides timezone.

Absolute timestamp in accessible text; refresh relative label.
Scope creep

UI work changes retry scheduling.

Keep queue policy out of the changed files.

Acceptance proof

BehaviorFixture job moves scheduled → retrying → exhausted with the expected labels.
Responsive UIList and detail states reflow at 320px with no page overflow.
AccessibilityKeyboard recovery path, named status, visible focus, and screen-reader timestamp.
