Concept lesson · one invariant

Retry the request, not the effect.

An idempotency key lets a server recognize that two network requests represent the same intended action. The client may retry; the server performs the action once and returns the saved result.

MissionAfter this lesson, you should be able to explain where the key is created, what the server stores, and why generating a new key on retry defeats the protection.

The invariant

All attempts for one user intention carry the same key. Different intentions carry different keys.

Attempt 1

Client sends payment

Idempotency-Key: pay_7F2. The network drops after the server commits.

Attempt 2

Client retries

The same body and the same key reach the server.

Result

Server returns receipt

It finds pay_7F2, skips the charge, and returns the stored response.

The boundary that matters

Wrong · new key per attempt

pay_7F2 then pay_9A1. The server sees two intentions and may charge twice.

Right · one key per intention

pay_7F2 on both attempts. The server can replay the original result.

Check the mental model

A user double-clicks "Pay", but the UI creates a fresh idempotency key for each click. What can the server safely conclude?

Choose an answer, then explain why before reading the feedback.

Edge case

What if the same key arrives with a different request body?

Reject it. A key identifies one intention and its original parameters. Reusing it with different input is ambiguous and should not silently return or perform a different action.
